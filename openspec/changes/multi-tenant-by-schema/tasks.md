**Raised during 7.1, then FIXED (owner call, 2026-08-04).** The first implementation of the header-less fallback used `IMembershipRepository.findActiveByUserId`, a `findFirst` with no ordering. The master `Membership` schema is unique only on `(userId, companyId)`, so a user genuinely CAN hold ACTIVE memberships in several companies — that is the point of multi-tenancy. Such a user calling without `X-Company-Id` got whichever row Postgres returned first, silently. That contradicts the spec's own wording, which allows the fallback only for the caller's **sole** ACTIVE `Membership`; with two there is no sole membership to fall back to. The port now exposes `listActiveByUserId` (every ACTIVE row, so the ambiguity is visible to the caller rather than hidden in the repository) and the guard rejects the ambiguous case with `400` naming the required header. Zero active memberships still takes the existing `403` path — the ambiguous case is a client error, not an authorization one, since the caller may be entitled to both. Proof: `tenant-context.guard.spec.ts` "rejects with 400 when the caller has SEVERAL ACTIVE memberships", `prisma-membership.repository.spec.ts` "returns EVERY ACTIVE Membership, never just the first".

**Column list settled (evidence, not assumption):** `TemplateCategory`/`TemplateProduct` (`prisma/master/schema.prisma`, already landed in task 3.1) are an EXACT field-for-field mirror of tenant `Category`/`Product` (`prisma/tenant/schema.prisma`), minus only the inverse relations (`stockLevels`, `movements`, `orderLines`, `commissionReference` on `Product`) that don't exist on a template row — confirmed by direct diff of both model blocks, not by re-deriving from `catalog.json`/`seedProducts` from scratch. `seedProducts` (`src/product/seed.ts`) itself only ever writes `name`/`slug`/`order`/`active` on `Category` (never `image`/`icon` — catalog.json's categories carry only `id`/`name`) and `name`/`description`/`price`/`priceCurrency`/`cost`/`costCurrency`/`categoryId`/`image`/`order`/`active` on `Product` (`percentDiscountPrice`/`discountPrice` always zero, `isNew` always `false`, `sku`/`barcode` never set) — `seedTemplateCatalog` (this batch, `src/product/seed.ts`) mirrors that exact write shape onto `templateCategory`/`templateProduct`, and `copyCatalog` copies the FULL column set (every one of `TemplateCategory`/`TemplateProduct`'s own columns, including ones the seed never populates, e.g. `image`/`icon` on `Category` would carry through if ever set directly on a template row) straight across without a narrower allow-list — the model's own field list is copy-catalog's contract, not seed.ts's write pattern.

**copyCatalog's idempotency + no-live-reference strategy:** tenant `Category`/`Product` rows are upserted keyed on `id`, reusing the SAME `id` as their master template row. This is safe because Prisma forbids a cross-schema `@relation` (design.md §1) — there is no FK from a tenant row back to its master template, so sharing the id value is not a live reference, only a copy-time convenience that makes `Product.categoryId` resolve correctly within the tenant schema without a separate id-remapping table, and makes re-running the copy a plain `upsert` with no duplicate-detection logic needed.
